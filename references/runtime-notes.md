# Runtime notes

- The skin launches the Store-installed `ChatGPT.exe` with `--remote-debugging-port=<port>` and injects through CDP.
- Themes are scanned at injector start from `themes/` and `themes-private/` (folders containing `theme.json`; see `THEME-SPEC.md`). Adding or editing a theme requires re-running `start-dream-skin.ps1` so the daemon rebuilds its payload; the running renderer keeps the old payload until then. `node scripts/injector.mjs --themes` prints the scan result without touching the app.
- Invalid themes are skipped (and unscoped `extra.css` files rejected) with `[dream-skin]` warnings on stderr — check `%LOCALAPPDATA%\CodexDreamSkin\injector-error.log` when a theme silently fails to appear.
- Theme/layout switching is programmatic only (`scripts/set-theme.mjs`); the selection persists in the renderer's localStorage under `codex-dream-skin.theme` / `codex-dream-skin.layout` and survives reloads, restore/reapply cycles, and watcher-recovered restarts. The default theme comes from `"default": true` in a theme.json (fallback: first scanned theme); the default layout is `fullscreen`.
- The default production port is `9335`; test instances may use another port plus an isolated `--user-data-dir`.
- CDP is bound to loopback. Do not expose it on a LAN interface.
- **Loopback stack is not stable across reboots**: Chromium may bind the DevTools server to `127.0.0.1` or to `[::1]` only (observed switching after a Windows reboot on 2026-07-15; hosts-file localhost entries do not decide it). Every probe — injector, launcher, watcher — must try both `http://127.0.0.1:<port>/json/list` and `http://[::1]:<port>/json/list` and accept either. Hardcoding IPv4 caused a watcher kill-loop that looked like Codex "闪退" while the app was actually healthy on `[::1]`.
- The watcher has a circuit breaker: after `MaxConsecutiveFailures` (default 3) failed recoveries it stops touching Codex for `CooldownMinutes` (default 30), logging the suspension. Codex keeps running unskinned during cooldown; a healthy skin state (CDP + injector) resets the counter automatically. The watcher must NEVER kill-loop Codex — any change to recovery logic must preserve this property.
- **Single probes are not trustworthy**: while Codex boots (session restore, window churn), `/json/list` can transiently return no `app://` page or time out even though the skin is fine. Observed on 2026-07-15: a freshly recovered instance was re-killed 6–15 s after a successful verification because one probe flaked, producing a "successful-restart loop" that the failure-based breaker cannot catch. Two watcher defenses exist and must both stay: (1) debounce — `ProbeFailuresBeforeRecovery` (default 3) consecutive missed probes are required before any recovery, with a 3 s HTTP timeout per probe and `LaunchGraceSeconds` (default 15) of leniency for young processes; (2) restart rate limit — at most `MaxRestartsPerWindow` (default 2) Codex restarts per `RestartWindowMinutes` (default 10), beyond which auto-recovery suspends for `CooldownMinutes` even if every restart "succeeded".
- After force-killing `ChatGPT.exe`, Windows may auto-respawn it without the debug flag; the respawn can win the single-instance race and silently drop CDP. The launcher waits for the process list to actually drain, swats late respawns, and retries the flagged launch once before giving up.
- The injector polls page targets and reinjects after document loads. In-page route changes use a debounced observer plus a low-frequency safety check to avoid CPU churn during streamed tasks.
- Target selection is intentional: only the main `app://-/index.html` page receives the skin. Compact and `initialRoute` pages are treated as auxiliary windows; the daemon removes stale Dream Skin state from them so desktop-pet transparency survives upgrades, reloads, and prior buggy injections.
- `%LOCALAPPDATA%\CodexDreamSkin\state.json` records schema/component, port, PID, script path, executable path, skill root, and the real process start time. Replacement and restore compare the executable plus exact argv position (`node` entry point or the token immediately after the unique PowerShell `-File`) before acting on a recorded PID. Ownership or inspection failure preserves state and fails closed.
- `install-dream-skin.ps1` creates `Codex Dream Skin Watcher.lnk` in the current user's Startup folder and starts it immediately. The watcher does not launch Codex by itself; it only reacts when Codex is opened normally without the required debug port.
- `%LOCALAPPDATA%\CodexDreamSkin\watcher-state.json` records the same ownership metadata for the watcher, and `watcher.log` records recovery events. A named mutex prevents duplicate watchers. `install-dream-skin.ps1 -NoAutoRecover` removes the Startup shortcut first, safely reconciles recorded watcher state, and refuses to claim success when a watcher mutex exists without trustworthy ownership state.
- If Codex is already running without the chosen debugging port, close it first or explicitly use `-RestartExisting`.
- Store updates are supported because the launcher queries `Get-AppxPackage OpenAI.Codex` on every launch.
- Restore is phased: watcher state/stop, injector state/stop, live DOM removal, optional shortcut uninstall, and optional base-theme restore report independently. A live or process failure does not skip requested local phases; any failed phase makes the final process exit nonzero.
- Windows lifecycle release evidence comes from `tests\windows-powershell-selftest.ps1` on GitHub `windows-latest` with Windows PowerShell 5.1 and Node.js 22. It covers owned/not-running/stopped/failure states, wrong executable/argv, state preservation, `-NoAutoRecover`, and restore continuation. macOS static checks remain a declared compatibility boundary.
